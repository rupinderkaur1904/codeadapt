# Decision log

Lightweight ADRs. Each entry: context, decision, consequences. Superseded entries are kept
and marked, never deleted.

## ADR-001 — Greenfield; nothing imported from the previous implementation (2026-10-15)
**Context:** the previous CodeAdapt became cluttered. **Decision:** start from an empty
repository; no code, schema or configuration is copied. **Consequences:** every component
is justified here; earlier lessons are used only as design warnings.

## ADR-002 — Python backend, single package with enforced module boundaries (2026-10-15)
**Context:** the research workflow (metrics, replay, notebooks) and the product share the
same domain logic. **Decision:** one Python package (`codeadapt`) with packages for
execution, content, evidence, diagnosis, adaptation, db, worker, api, research; diagnosis
and adaptation are pure. **Alternatives:** microservices (rejected: no scaling need,
more failure modes); Go/Rust runner (rejected for now: container start-up dominates cost).
**Consequences:** module rules are documented in architecture §3.1; an import-linter
contract can enforce them from M3.

## ADR-003 — Container-per-compile and container-per-test isolation via Docker CLI (2026-10-15)
**Context:** untrusted C++ must be isolated; developers may be on Windows/macOS; a timeout
is not a sandbox. **Options:** (a) rlimits/seccomp on host processes — weak, Linux-only;
(b) bubblewrap/nsjail — strong and fast but Linux-only and not installed on typical
student/dev machines; (c) Docker with hardened flags — portable, well understood, can
switch runtime to gVisor; (d) Firecracker — strongest, heavy for MVP. **Decision:** (c),
with production requiring the gVisor runtime; code talks to a `SandboxBackend` protocol so
(b)/(d) can be added. Code enters via tar-on-stdin into a per-job named volume; no host
bind mounts. One container per test gives clean test-to-test isolation (measured
start-up ≈ 0.3 s on the dev host). We drive the `docker` CLI via asyncio subprocesses
rather than the Docker SDK: fewer dependencies, identical semantics to what operators
debug by hand. **Consequences:** the worker host holds a root-equivalent socket → runner
runs on a dedicated host in production (security.md §2).

## ADR-004 — PostgreSQL with a DB-backed job queue; SQLite for fast tests (2026-10-15)
**Decision:** jobs live in a `jobs` table claimed with `FOR UPDATE SKIP LOCKED`; no Redis or
Celery. SQLite is supported for unit tests/local dev by keeping SQL portable (the queue
falls back to a single-worker lock on SQLite). **Consequences:** durable, inspectable jobs;
one fewer service. Revisit if queue latency matters.

## ADR-005 — Diagnosis v1 = executed fingerprints + strict consistency + abstention (2026-10-15)
**Context:** no labelled real-world data; claims must be explainable and falsifiable.
**Decision:** error models are executable mutants; predictions come from running them;
decisions follow methodology §4; output is counts, not probabilities.
**Consequences:** high precision, limited coverage (double bugs abstain); coverage is reported.
Better methods plug in via `DiagnosticMethod` and are compared by replay.

## ADR-006 — React + TypeScript SPA after the backend loop works (2026-10-15)
**Decision:** frontend begins at M4, typed from OpenAPI. **Consequences:** M1–M3 are
exercised through CLI and API tests; avoids building UI on unstable contracts.

## ADR-007 — Server-side sessions, Argon2id, three roles (2026-10-15)
**Decision:** no external IdP for the MVP. Dev-only stub auth in M3 is hard-disabled
outside `CODEADAPT_ENV=dev`. Full auth lands in M8, before any non-local deployment.

## ADR-008 — Data classes on every record (2026-10-15)
**Decision:** `data_class ∈ {real, synthetic, dev}` on users, submissions and derived
records; synthetic fixtures are generated by a separate path and never through student
accounts; research queries must filter explicitly. **Consequences:** synthetic results can't
silently mix into real-learner statistics.

## ADR-009 — Public repo holds only demo content; real content in a private repo (2026-10-15)
**Context:** the GitHub repository is public. Hidden tests, reference solutions and error
models must not be visible to study participants. **Decision:** this repo ships
`content/demo/` (explicitly *not secret*) for development and CI; real study content
lives in a separate private repository mounted through `CODEADAPT_CONTENT_DIR`.
**Status:** confirmed by the owner on 2026-10-15 (chose public repo + private content repo
over making this repository private).

## ADR-010 — uv, ruff, mypy strict, pytest (2026-10-15)
**Decision:** uv lockfile for reproducible installs; ruff for lint+format; mypy `--strict`
on `src/`; pytest with a `sandbox` marker for Docker-dependent tests (skipped with a reason
when Docker is absent; CI always runs them).

## ADR-011 — Sandbox containers run with an init process (2026-10-15)
**Context:** M1 testing showed that a submission running as PID 1 ignores default-action
signals, so the CPU rlimit (SIGXCPU) could not stop it. **Decision:** every sandbox
container uses `--init` (Docker's bundled tini). **Consequences:** the program is an
ordinary process; one extra PID counts against `--pids-limit`; signal exit statuses are
reported as 128 + N by the init and classified accordingly.

## ADR-012 — Content as TOML + C++ files; outcome signatures as the comparison unit (2026-10-15)
**Context:** problems need tests, probes, skills and executable error models in a format
authors can review in a diff. **Decision:** `problem.toml` (stdlib `tomllib`, no extra
dependency) plus plain C++ files; versions are content hashes. Behaviour is compared through
*outcome signatures* (normalised stdout, or runtime-error signal/exit, or limit kind), so
fingerprints, validation and diagnosis all use one definition of "behaves the same".
Authors also write `expected` outputs, and the executed reference must match them, which
catches harness and reference bugs. **Consequences:** a harness that prints
non-deterministic text (addresses, timing) would be rejected by validation, which is intended.

## ADR-013 — M3 slice conventions (2026-10-15)
* **Dev-only auth stub:** in `dev`/`test`, the `X-Dev-Role` header selects a fixed dev account
  (`data_class = dev`). It is disabled in production, where endpoints return 503 until M8.
  This keeps the slice testable without building auth twice.
* **Fingerprint cache:** the worker measures fingerprints the first time a
  `(problem version, environment)` pair is seen. It stores them with their validation
  report in `fingerprint_sets`, and refuses to diagnose against content that failed
  validation.
* **Queue claim:** an optimistic conditional `UPDATE` (expected state + attempt count). It is
  portable across SQLite and PostgreSQL, so `SKIP LOCKED` is not required (refines ADR-004).
* **Student projection:** hidden tests are shown only by number and `student_description`.
  An error model's `student_hint` is shown only for `HYPOTHESIS_SUPPORTED`. Model keys and
  descriptions never reach students. An end-to-end test asserts this.

## ADR-014 — CodeMirror 6 instead of Monaco (2026-10-15; supersedes the editor choice in ADR-006)
**Context:** Monaco is about 2–3 MB, loads web workers, and its React wrapper fetches from a
CDN by default. That is a third-party runtime dependency and a CSP problem for a study
deployment. **Decision:** CodeMirror 6 with `@codemirror/lang-cpp`, bundled locally and
lazy-loaded with the practice page (about 210 kB gzipped). **Consequences:** it has no
IntelliSense, which a learning platform does not want anyway.

## ADR-015 — Development compose stack uses SQLite and the host Docker socket (2026-10-15)
**Decision:** `compose.yaml` runs migrate, API, worker and the Vite dev server. The worker
mounts the host Docker socket so it can start sandbox containers. It is marked dev-only,
because the socket is root-equivalent; the production layout is decided in M8. It uses
SQLite on a shared volume because that is the tested configuration (PostgreSQL arrives with
M8 and its own tests).

## ADR-016 — Reliability channels: one repeat of failing tests, sanitiser build over all tests (2026-10-15)
**Context:** undefined behaviour can make output wrong, or right by accident, and a timeout
alone hides nothing about it. **Decision:** run the ASan + UBSan profile on every test, and
repeat only *failing* tests, once, to detect non-determinism. Passing tests are not
repeated: a non-deterministic pass is still a pass on that run, and the sanitiser covers
the main cause. Sanitiser findings exclude a test; the diagnosis treats exclusions under
rule 3. **Costs:** about twice the execution per submission, and the first fingerprint
measurement for a content version takes about 90 s locally. **Limits:** uninitialised
reads are not detected (no MSan in GCC).

## ADR-017 — Adaptation v1: append-only recommendations, criterion verdicts (2026-10-15)
**Context:** M6 needs a next-exercise policy and a way to judge the follow-up without
claiming learning. **Decision:** the policy (`rule_policy` v1) and the evaluation
(`criterion_check` v1) are pure functions over stored evidence. Their output goes into
append-only `recommendations` and `followup_evaluations` tables; a learner's open
recommendation is the latest one without an evaluation, so nothing is updated in place.
Each recommendation records its success criterion *before* the follow-up exists. Verdicts
are `criterion_met` / `criterion_not_met` / `not_comparable` rather than "improved",
because without a comparison condition a met criterion is equally consistent with an
easier problem. Candidate problems are limited to the index problem's family, and skills
are matched by key across problems. Adaptation runs after the diagnosis is committed, so a
failure in it is logged and never loses evidence. **Costs:** the ledger is rebuilt from
the learner's whole history on every diagnosis (fine at pilot scale; index it later if
needed). **Limits:** a recommendation can only target skills that the content's probes
and error models name, and its ranking ties are broken by slug, which is arbitrary but
deterministic.

## ADR-018 — Evaluation harness shares the worker's evidence path; dev role switch in the UI (2026-10-15)
**Context:** M7 must report methodology §6.1 metrics, and a harness that collected
evidence differently from the worker would measure a different system. **Decision:**
evidence collection moved to `evidence/collect.py`, used by both the worker and
`codeadapt-eval`. The harness writes no database rows and its reports carry no
timestamps, so reruns compare byte for byte. Held-out cases live in `eval/heldout/` with a
`cases.toml` manifest per problem (`truth` = error-model key, `correct` or `unmodelled`).
The research API reports counts only, since stored submissions have no ground truth.
Until real authentication exists (M8), the web app has a "development role" selector that
sets the `X-Dev-Role` header; the API ignores it outside development. **Limits:** the
harness runs every case's evidence concurrently, so runtime grows with the sandbox host's
capacity; cross-environment reproducibility is not yet measured.

## ADR-019 — Evidence no stronger than its support: explained-failure ledger, behaviour groups, qualified hypotheses (2026-10-15)
**Context:** the lower-bound design review found that (a) the ledger charged every failing
test to every skill its probes name, whether or not anything explained the failure, and
(b) `min_support` counts tests, so a model whose supporting tests all show one behaviour
(E2 `hi_init_last_index`, in all three demo problems) looked better supported than it is.
The owner asked for these to be fixed, and for the stricter support rule (C6) to be
compared with v1 on held-out cases before any adoption. **Decision:**
* *Ledger (C5).* A failed test enters the skill ledger only when a supported diagnosis
  explains it, and then only under the selected model's skill (`explained_by` records the
  model). Failures in ambiguous, unmodelled, insufficient or unreliable attempts stay in
  the stored submission but are not skill evidence. Passed and excluded tests are
  attributed through probes as before. Policy version → `rule_policy` 1.1.
* *Behaviour groups.* `diagnosis/groups.py` measures them; validation and diagnosis share
  it. Diagnosis v1.1 records `support_behaviours` and, for a supported diagnosis resting on
  one group, `evidence_strength = single_behaviour` with a qualification. Its *decisions*
  are those of v1. A supported diagnosis that is single-behaviour, or whose model has a
  `known_limitation`, is a *qualified hypothesis*: the student sees "one possible cause to
  check", the recommendation says the pattern "has more than one possible cause", and its
  rationale carries `qualified_hypothesis`. The follow-up still targets the skill.
* *C6 candidate.* `v2-candidate` (same method, `min_behaviours = 2`) turns single-group
  diagnoses into `INSUFFICIENT_EVIDENCE`. It is selectable in `codeadapt-eval --method`
  only; the worker keeps v1.1. Adoption is an owner decision (see the review-resolution
  report for the measured trade-off).
* *Follow-up relation.* Each evaluation records whether the follow-up was the same
  problem, equivalent practice or a linked transfer problem (`criterion_check` 1.1,
  migration 0003). A met criterion is reported as passing the follow-up's tests, never as
  mastery or demonstrated transfer.
* *Declared intent (C4).* `problem.toml` gains per-test `purpose` and `distinguishes`,
  per-model `known_limitation` and `[curriculum]` links; validation errors on a declared
  `distinguishes` that the measurement contradicts. Calibration cases (written after a
  design analysis) live in `eval/calibration/` and are never pooled with held-out ones.
**Costs:** behaviour groups are relative to the modelled programs, so adding a model can
change a diagnosis's strength; content changes are therefore versioned as before.
**Limits:** a qualified hypothesis is still a hypothesis from the modelled error space;
the qualification describes the evidence, not the probability of being right. The O(log n)
requirement is not assessed by any test (see methodology §4).

## ADR-020 — Sandbox runs under load: longer kill wait, untrusted streams are infrastructure errors (2026-10-15)
**Context:** on busy hosts (locally and on CI), `docker kill` of a timed-out container
sometimes exceeded its 15 s limit, aborting a job, and once a run reported exit 0 with
empty stdout, which made validated content look non-deterministic. 200 stressed local
runs did not reproduce the lost output. **Decision:** the kill wait uses the general
60 s CLI limit (the workload stays bounded by its CPU rlimit, memory and pids limits, and
`rm -f` still runs afterwards). When the `docker run` client's exit status differs from
the container's own exit code on a run that ended by itself, the run is classified as an
infrastructure error, never as program output. Fingerprint measurement re-measures an
infrastructure error up to 3 times; program behaviour is never re-measured, so real
non-determinism is still reported. **Limits:** if a lost-output run reports matching exit
statuses, this check does not catch it. A harness end-of-output marker would, but it
changes every problem's output contract, so it is proposed rather than done.
**Status (2026-10-16):** the original CI lost-output failure is **not shown to be fixed**:
it was never reproduced, so no test reproduces it. CI has passed since this change, which
is consistent with a fix but does not demonstrate one. `tests/unit/test_docker_cli.py`
drives `DockerSandbox` through a scripted fake `docker` binary and checks how the two
observed conditions are *reported*: a client/container exit-status disagreement becomes an
infrastructure error, a kill slower than the old 15 s limit (scaled down) still yields a
time limit, and a kill slower than the wait raises `SandboxUnavailableError`. That last
test found a defect: when the workload kill itself failed, the local `docker run` client
was left running. `run_bounded` now always stops the client in that case (the container
is still removed by `rm -f`). These tests use a fake daemon, so they say nothing about
whether real Docker loses output under load.

## ADR-021 — Modelling architecture: deterministic diagnosis plus a later Bayesian learner model (2026-10-16)
**Context:** the owner set the long-term direction (project chat, 2026-10-16): keep the
execution-grounded diagnosis, and add Bayesian learner modelling later as a separate layer.
**Decision:** four components with separate responsibilities, each testable on its own:
1. *Diagnostic engine* (fingerprint consistency, ADR-005/019). It identifies which known
   implementation-error patterns are consistent with one submission's execution evidence,
   or abstains. It stays deterministic. It is not to be replaced by an ML or LLM bug
   classifier: there is no labelled real-student dataset, and the current method is
   reproducible, interpretable and traceable.
2. *Skill-evidence layer* (today: the ledger, `adaptation/ledger.py`). It maps reliable,
   diagnosis-supported observations to skills, keeps their uncertainty, and makes no
   unsupported attribution. Since ADR-019, failures from ambiguous, unmodelled,
   insufficient or unreliable attempts are not skill evidence; infrastructure failures
   never reach it.
3. *Bayesian learner model* (planned, **not implemented**). It updates estimated skill
   mastery as valid evidence accumulates across attempts and problems.
4. *Recommendation policy* (today: `rule_policy`). It chooses next activities from the
   learner model, prerequisites, curriculum links and available exercises.

A diagnosed implementation pattern is never treated as proof of a misconception or of a
lack of mastery. **Sequencing:** the interface between the four components (the evidence
each receives, how uncertainty is represented, which observations are excluded) is
documented first, for the owner's review. Only when the evidence layer is reliable enough is a
separate, testable BKT milestone proposed. Its initial probabilities and its transition,
guess and slip parameters are documented as assumptions until validated. Synthetic
experiments may test implementation behaviour, but are never presented as calibration on
real students or as learning gains. **Supersedes** the methodology §5 note that placed
BKT only after a cohort study: BKT is part of the intended architecture, gated on the
evidence layer and the reviewed interface, and its parameters stay assumptions until real
data validates them.

## ADR-023 — Component interfaces and evidence rules (2026-10-17)
**Context:** ADR-021 requires the contracts between the diagnostic engine, the
skill-evidence layer, the learner model and the recommendation policy before any Bayesian
work, and the owner required that a load-induced timeout never becomes student-failure
evidence. **Proposal:** docs/component-interfaces.md: CPU-limit timeouts are program
evidence; wall-deadline-only timeouts are re-run and otherwise `inconclusive`; ledger
policy 1.2 (qualified diagnoses add no failure evidence; one observation per attempt and
skill); a skill-map snapshot per content version; an end-of-output marker later.
**Status (2026-10-17, milestone EV1):** D1–D4 implemented, within the authority the owner
set that day (D2 approved in principle the same day). `evidence_rules_version` 1 and ledger
policy 1.2 are recorded with each diagnosis and recommendation. Held-out and calibration
results are unchanged case for case. A sandbox test drives 12 concurrent infinite loops
under host CPU load: locally each first hit the wall deadline, and each ended as a CPU-limit
time limit after the re-run. The CI event (a trivial run recorded as a time limit) was not
reproduced, so R2 is shown to classify a scripted stall correctly, not shown against that
event. D5 was superseded by ADR-024 (a runner-level marker that changes no content version). gVisor delivery of SIGXCPU is untested: if `runsc` did not
deliver it, genuine timeouts there would become inconclusive (evidence lost, not invented).

## ADR-024 — End-of-output marker in the runner (2026-10-17)
**Context:** CI on commit d3919b0 rejected the lower-bound content: `hi_skips_candidate`
on test `empty` produced one run with exit 0 and **empty stdout** and one run printing
`0`. The program is deterministic (n = 0, the loop never runs) and was validated with 3
repeats locally. The client and the container reported the same exit status, so the
ADR-020 mismatch check did not fire. This is the lost-output failure of ADR-020 observed
again, and it shows that the mismatch check alone does not catch it. Its root cause
(somewhere in the attached-stream path between container and host) is still unknown.
**Decision:** each test run now executes the binary under a small Perl wrapper that,
after the binary exits, writes a random per-run marker to stdout and stderr and exits
with the binary's status (128 + N for signal N, as before). A run that ended by itself
without both markers is an infrastructure error (`output_incomplete`), re-measured like
any infrastructure error and never evidence. This is done in the runner, not in the
problem harness, so no content version changes (the D5 alternative in
docs/component-interfaces.md would have changed all of them). `evidence_rules_version`
becomes 2. Perl is used instead of `sh` because dash appends "Segmentation fault"-style
notices to stderr. **Validated:** a fake-docker test reproduces the observed shape (exit 0
from both sides, empty stdout) and it is classified as an infrastructure error; program
stdout, stderr and exit status are unchanged on real runs (normal, segfault, abort,
non-zero exit, CPU limit); held-out and calibration results unchanged. **Not validated:**
that the marker catches the real event (it has not recurred since); a submission that
kills its parent process makes its runs infrastructure errors (no evidence, never false
evidence). **Cost observed:** the CI backend job on d3919b0 took 1670 s against about
1000 s before EV1, consistent with the ADR-023 stall re-runs of looping models on a busy
runner.

## ADR-025 — LM1: researcher-only Bayesian knowledge tracing (2026-10-17)
**Context:** EV1 made skill observations reliable, behaviour-level and tied to content
versions (ADR-023, ADR-024). ADR-021 called for a separate, testable BKT milestone after
that. The proposal is in docs/proposals/lm1-learner-model.md. The owner approved it on
2026-10-17 with these decisions:
- L1(a): count only the first reliably evaluated attempt per problem version;
- L2: the proposed parameters, explicitly as assumptions;
- L3: estimates visible to researchers only;
- L4: build LM1 before CE1.

**Decision:** `codeadapt.learner.bkt` implements standard BKT per skill (model
`bkt-standard` 1) over `skill_observations()` with parameter set `bkt-params-assumed-1`
(P(L0) 0.3, P(T) 0.1, P(G) 0.2, P(S) 0.1, not fitted or calibrated). The rules:
- Attempts that were not reliably evaluated (compile error, execution error, unreliable
  evidence) do not use up the counted attempt.
- Retries stay listed as uncounted, with a reason.
- Distinct problems are counted by slug, while each observation keeps its exact version.
- No value is shown below 3 counted observations from 2 problems. This is a display
  threshold, not an accuracy criterion.

Estimates are computed on read and not persisted. They are exposed only at
`GET /api/v1/research/learner-model` and on the console page, always labelled "estimated
under assumed parameters". Student responses, diagnosis, feedback and recommendation
policy v1.2 are unchanged. A test checks that only the API module imports the learner
model.

**Validated technically:**
- update arithmetic against hand calculations, for both outcomes and for a two-step
  sequence;
- parameter constraints;
- deterministic recomputation, independent of input order;
- excluded evidence never changes an estimate;
- retry counting, version identity and the display threshold;
- student responses unchanged.

**Not validated:**
- whether any estimate reflects what a learner knows;
- the parameter values;
- the skill map;
- BKT's independence, no-forgetting and shared-parameter assumptions.

All of these need real-learner data, which the project does not have.

## ADR-026 — Policy v1.3: non-recommendable problems (CE1 decision E2, 2026-10-18)

**Context.** Policy v1 chooses follow-ups from every problem in the index problem's family.
Adding CE1's problems to `binary-search` would change which problems it recommends with no
policy decision. The owner chose option (b) on 2026-10-17: new problems stay out of v1's
candidate set until a separate policy decision on prerequisite step-back and transfer.

**Decision.**
- Content gains `recommendable` (default `true`). First-true is the first problem with
  `recommendable = false`.
- Policy v1.3 drops non-recommendable problems from its candidate set. No rule changes. A
  non-recommendable index problem can still be the retry fallback, as in v1.2 when no
  candidate probes the skill.
- A non-recommendable problem stays in the problem list. Its attempts are diagnosed, enter
  the evidence ledger and skill observations, and feed the researcher-only learner model.
- The flag is not shown to students.

**Check.** A golden file of 286 synthetic recommendations, produced by policy 1.2 at
`89a7803` over the three original problems, must be reproduced exactly with first-true in
the catalogue (`tests/unit/test_adaptation.py`). These histories are synthetic and exercise
the rules; they are not learner data.

## ADR-028 — Sandbox flags under gVisor (2026-10-22)
**Context:** the production tier requires `runsc` (ADR-003), but it had never been run. Under
`runsc` release-20261005.0 (systrap) with the unchanged flags, 26 of 33 sandbox tests failed:
(1) the container's pids cgroup also holds gVisor's own host threads (about 30 at start-up),
so `--pids-limit 16` stopped every run container from starting, and with a larger limit a
fork bomb exhausted it and crashed the sandbox, which the runner reported as an
infrastructure error (no markers) instead of failed `fork()` calls; (2) gVisor mounts a
writable tmpfs at `/tmp` when the container has none, so a run could write `/tmp`.
**Decision:** only when the runtime is `runsc`: the guest process limit is
`--ulimit nproc=<pids>` (gVisor enforces it per sandbox; the fork-bomb test still sees at most
15 children), the pids cgroup becomes `<pids> + 256` as a host-side backstop, and run
containers get `--tmpfs /tmp:ro`. runc flags are byte-for-byte unchanged (unit test), because
under runc the sandbox uid is shared by every container, so `RLIMIT_NPROC` would not be per run.
**Validated:** all 33 sandbox tests pass under `runsc` locally (about 20 min against 18 min
under runc); `tests/unit/test_sandbox_flags.py` pins the flags for both runtimes; a CI job runs
the `core` shard under `runsc`. **Not validated:** the deployment host; whether runc and runsc
give identical observations for every content test (methodology §6.1 cross-environment
reproducibility is still unmeasured); the headroom under heavily multi-threaded programs.
No content, evidence rule, diagnosis or feedback change.

## ADR-029 — Real authentication, request limits and an audit log (M8, 2026-10-22)
**Context:** ADR-007 chose server-side sessions, Argon2id and three roles, and left the
implementation to M8. Until now only the dev stub existed, and production answered 503.
**Decision:**
- *Accounts:* there is no self-registration. An operator runs `codeadapt-admin create-user`
  with an explicit role and data class. Passwords are read without echo or from stdin,
  never from arguments, and must have at least 12 characters. They are hashed with
  Argon2id (argon2-cffi defaults, RFC 9106 low-memory profile) and rehashed on login when
  those parameters change. `set-password` and `disable` end all of the account's sessions.
- *Sessions:* `POST /api/v1/auth/login` sets a random 256-bit token in the
  `codeadapt_session` cookie: HttpOnly, SameSite=Strict, Path=/api, Secure in production,
  12 h by default (`CODEADAPT_SESSION_HOURS`). Only its SHA-256 is stored. Logout revokes
  the session server-side. A wrong password, an unknown user, an account without a
  password and a disabled account all give the same 401, and unknown users are checked
  against a dummy hash so the timing matches.
- *CSRF:* each session has its own CSRF token, returned by login and `GET /auth/me`. Every
  request other than GET, HEAD or OPTIONS made with the cookie must send it in
  `X-CSRF-Token`. This comes on top of SameSite=Strict.
- *Limits:* after 5 failed logins for a username or from a client address within 15 min,
  login answers 429, even with the right password. Each user may create
  `CODEADAPT_SUBMISSIONS_PER_MINUTE` submissions per minute (10 in production, unlimited in
  dev and test).
- *Audit log:* the append-only `audit_events` table records logins, failed and throttled
  logins, logouts, account changes, every researcher-endpoint request (path and query),
  and every time staff opens another user's submission. It never stores passwords, tokens
  or source code.
- *Dev stub:* the `X-Dev-Role` header still works in dev and test, but only when there is
  no session cookie. In production it is ignored and requests without a session get 401.

**Validated:** `tests/unit/test_auth.py` covers the hash format, the cookie attributes, the
digest-only storage, identical failures, CSRF (missing, wrong, right), logout replay,
expiry, disabled accounts, login throttling, the submission limit, both audit kinds and the
admin CLI. Migration 0005 matches the models.
**Web (same day):** a login page shown when the API answers 401, the CSRF header on every
non-GET request, the signed-in username with a logout button, and the dev role switch only
under the stub. Vitest covers wrong and right passwords, logout and the stub; a Playwright
test logs in with a real account through the browser and checks the cookie attributes.
The dev stub also no longer fails with a 500 when two first requests race to create the
dev account (seen in the browser test).
**Not done:** the client address behind a reverse proxy
(needs the deployment's trusted-proxy setting); password reset by email (none planned);
data retention for `audit_events` (needs an owner decision with M9). No change to
diagnosis, feedback, recommendations or the learner model.

## ADR-031 — Fenced job completion and no re-run of a diagnosed submission (2026-10-24)
**Context:** `queue.finish` and `queue.requeue` updated a job by id alone. A worker whose lease
expired (600 s) could overwrite the state of the attempt that another worker had reclaimed. A
worker that died after committing its diagnosis but before finishing the job left it to be
reclaimed and run again. That run added a second, possibly different diagnosis and a second
recommendation. The learner model reads the latest diagnosis, so the evidence could change
silently.
**Decision:** `finish` and `requeue` change a job only while it is still the caller's claim
(running, same worker, same attempt) and return whether they did. Before running, the worker
looks for a diagnosis by its own method and version for the submission. If one exists, it
finishes the job without executing anything. Diagnosis rules, evidence rules, policy, ledger,
BKT and feedback are unchanged.
**Lease heartbeat (added 2026-10-24):** while a job runs, the worker renews its lease every
third of a lease period (`queue.renew`, fenced like `finish`). A long job (for example the
first submission, which measures fingerprints) is therefore not reclaimed while its worker is
alive. **Still not solved:** a worker that is alive but stalled (event loop blocked for a whole
lease) can lose its claim mid-run. Both runs then commit a diagnosis, and only the claim holder
finishes the job. Tests: `tests/unit/test_queue.py` (including a job that outlives two lease
periods), `tests/unit/test_pipeline_redelivery.py`.

## ADR-034 — Skill-taxonomy migration for the new families (L22, 2026-10-26)
**Context:** The audit and proposal L22 (docs/proposals/l22-skill-taxonomy.md) found two
problems with ADR-033's keys:
- `index_range` and `update_rule` pooled unrelated mechanisms;
- pivot-index declared `index_range` with no model, so that skill could only gain `correct`
  evidence.
**Owner decision (2026-10-26):** split `update_rule` into `window_maintenance`,
`pointer_movement` and `running_state`, and `index_range` into `loop_bounds` and
`range_inclusion`. The decision also says:
- give pivot-index a model for its mapped skill, or document a reason;
- create new content versions, without rewriting historical observations or converting old
  keys;
- mark retired keys as deprecated in researcher displays;
- validate unknown keys, retired keys and declared skills that no model can give evidence
  for;
- do not change BKT parameters, recommendation policy or recommendation outcomes;
- do not add the optional splits.
**Decision:**
- **One taxonomy.** `backend/src/codeadapt/content/taxonomy.py` holds every key a problem
  may declare (`ACTIVE`, with its definition). It also holds the retired keys (`RETIRED`),
  each with its historical definition, retirement date, this ADR and its replacements.
  Content validation rejects:
  - a retired key, naming its replacements;
  - an unknown key;
  - a definition that differs from the taxonomy's.
- **Model mapping.** The 13 new-family problems were remapped model by model, as proposed in
  L22 §2.1–2.2. Each probe was remapped to match its tests' models.
  - **pivot-index:** `pivot_counted_left` and `pivot_counted_right` move to
    `range_inclusion`. pivot-index now declares `tie_resolution`, `output_contract` and
    `range_inclusion`, and every declared skill has a model that can give negative evidence.
    Its former `update_rule` and `index_range` probes (`pivot_excluded`, `pivot_at_edge`,
    `negatives`, `large_input`) all map to `range_inclusion`. The tests that carry them are
    measured to separate the two `range_inclusion` models. Declaring `running_state` instead
    would add a skill with no model. *This is a judgement for review.*
  - **plus-one `adds_at_front`:** L22 suggested `output_contract`, renamed `io_contract`.
    That rename is one of the optional changes, which the owner did not ask for, so the
    model maps to `loop_bounds` instead. Its definition includes "runs from the right end".
    *This is a judgement for review.*
- **Optional splits not made:** `tie_resolution` is not split, and `output_contract` is not
  renamed.
- **Positive-only skills are explicit.** A declared skill with no model that can give
  negative evidence must carry a written reason under `positive_only_skills` in its
  problem.toml. That means no model maps to it, or every model that does carries a
  `known_limitation`. Validation rejects a missing reason, a stale reason (the skill does
  have a model) and a reason for an undeclared skill. 11 skills in 10 problems carry a reason
  (see ADR-036 and the evaluation record).
- **Historical observations are not converted.** An attempt keeps the skill-map snapshot of
  its own content version (ADR-023 D4). Observations made under `index_range` or
  `update_rule` stay under those keys. The researcher learner-model view shows them with a
  "deprecated" badge, the historical definition and the replacements (`retired_skills` in
  the API). Only dev and test databases hold attempts.
**Unchanged:**
- the four binary-search keys and their definitions;
- `accumulator_init`, `tie_resolution` and `output_contract`;
- the ledger, rule C, BKT parameters (`bkt-params-assumed-1`) and policy 1.4.

**Check against the previous HEAD (57b46d1).** 442 one-attempt synthetic histories covering
every problem: no-failure, unmodelled, every model named, and every model pair ambiguous.

- Rule, action, chosen problem and review flag are identical in all 442 cases.
- In 88 cases only the target and criterion skill names differ, because they are the new
  keys (docs/evaluation/l20-d1-l22-2026-10-26/).
**Consequences:**
- BKT pools by the new keys, with the same assumed parameters. More keys means fewer
  observations each.
- The student-facing focus text is built from skill definitions, so new recommendations name
  the new definitions for those problems. A recommendation stored before this change that
  targets a retired key still shows that key's historical definition
  (`api/recommendation.py`), rather than losing its focus text.
- Whether learners' errors cluster this way is as untested as before (L22).

## ADR-035 — No skill evidence from an attempt that names a banned library call (D1, 2026-10-26)
**Context:** 14 statements forbid named library calls, but a banned call passes every test, and
rule C then gives `correct` observations (L23; docs/proposals/d1-technique-evidence.md).
**Owner decision (2026-10-26):** implement P-D1a with these boundaries:
- detection from versioned problem metadata;
- no skill observations when a banned name is detected;
- submission, execution and diagnosis records preserved, and the attempt still counted in
  attempt and execution statistics;
- global rule C, the diagnosis rules and the recommendation policy unchanged;
- no claim that detection proves the algorithm or complexity;
- no new student-facing sentence;
- historical observations not rewritten.
**Decision:**
- **Versioned list.** `banned_names` in each problem.toml lists the statement's
  "Do not call" names exactly as written (for example `std::lower_bound`, `sqrt`). The
  loader rejects a list that differs from the statement's sentence, and the spec rejects
  invalid or duplicate names. The list is part of the content version and of the skill-map
  snapshot (`SkillMap.banned_names`).
- **Detection.** `adaptation/technique.py` uses a token match after removing comments and
  string, character and raw-string literals. It counts:
  - a qualified use (`std::name`, `std::ranges::name`, `using std::name`);
  - an unqualified call, as after `using namespace std` or for a C function such as `sqrt`.

  It ignores member calls, other namespaces and a function the program defines itself.
- **Where it applies.** When attempts are rebuilt from stored records (`attempt_record`),
  the stored source is checked against the banned names of the submission's own version
  snapshot. An attempt with a found name gives no skill observations. The check sits in
  `skill_observations`, before rule C; `build_ledger`, which the policy reads, is unchanged.
- **Researcher trace.** It shows `technique_check`: the banned names, the names found,
  whether skill evidence was withheld or eligible, and the limits of the check.

**What still happens to such an attempt.** It still runs, is still diagnosed, still produces
feedback and a recommendation, and still appears in metrics and attempt counts. For LM1 it
consumes the counted opportunity on its problem version, like an abstaining attempt with
reliable execution. That is option 1 of the proposal and needs no change to the counting
code. *This is a decision for review:* option 2 (not consuming the opportunity) would need a
BKT counting change.
**Before and after:**
- **Before:** an attempt that called a banned function and passed gave rule C `correct`
  observations for every probed skill. One that failed could give an `incorrect` observation
  from a named diagnosis.
- **After:** both give none. Attempts without a detected name are unaffected.
**Historical records:**
- Versions registered before this change have snapshots without `banned_names`, which parse
  as an empty list. Attempts on those versions therefore keep the observations they had.
- The new rule applies only to attempts on the new content versions. Nothing stored is
  rewritten.
- Only dev and test databases hold attempts.
- Replay: none of the 845 stored evaluation programs (held-out, calibration, mutation) names
  a banned call of its problem, so no evaluation result changes
  (docs/evaluation/l20-d1-l22-2026-10-26/banned_name_replay.txt).

**Limits.** Detection is static. It does not show which algorithm a program uses, that the
call is reached, or its complexity, and a program with no name found is not verified to use
the intended technique. A macro or a hand-written linear scan is not detected, so a `correct`
observation still means "no failure on the probing tests" (L23 stays).
