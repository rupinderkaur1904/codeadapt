# Decision log

Lightweight ADRs. Each entry: context, decision, consequences. Superseded entries are kept
and marked, never deleted.

## ADR-001 — Greenfield; nothing imported from the previous implementation (2026-10-15)
**Context:** the previous CodeAdapt became cluttered. **Decision:** start from an empty
repository; no code, schema or configuration is copied. **Consequences:** every component
is justified here; earlier lessons are used only as design warnings.

## ADR-002 — Python backend, single package with enforced module boundaries (2026-10-15)
**Context:** the research workflow (metrics, replay, notebooks) and the product share the
same domain logic. **Decision:** one Python package (`codeadapt`) with packages for
execution, content, evidence, diagnosis, adaptation, db, worker, api, research; diagnosis
and adaptation are pure. **Alternatives:** microservices (rejected: no scaling need,
more failure modes); Go/Rust runner (rejected for now: container start-up dominates cost).
**Consequences:** module rules are documented in architecture §3.1; an import-linter
contract can enforce them from M3.

## ADR-003 — Container-per-compile and container-per-test isolation via Docker CLI (2026-10-15)
**Context:** untrusted C++ must be isolated; developers may be on Windows/macOS; a timeout
is not a sandbox. **Options:** (a) rlimits/seccomp on host processes — weak, Linux-only;
(b) bubblewrap/nsjail — strong and fast but Linux-only and not installed on typical
student/dev machines; (c) Docker with hardened flags — portable, well understood, can
switch runtime to gVisor; (d) Firecracker — strongest, heavy for MVP. **Decision:** (c),
with production requiring the gVisor runtime; code talks to a `SandboxBackend` protocol so
(b)/(d) can be added. Code enters via tar-on-stdin into a per-job named volume; no host
bind mounts. One container per test gives clean test-to-test isolation (measured
start-up ≈ 0.3 s on the dev host). We drive the `docker` CLI via asyncio subprocesses
rather than the Docker SDK: fewer dependencies, identical semantics to what operators
debug by hand. **Consequences:** the worker host holds a root-equivalent socket → runner
runs on a dedicated host in production (security.md §2).

## ADR-004 — PostgreSQL with a DB-backed job queue; SQLite for fast tests (2026-10-15)
**Decision:** jobs live in a `jobs` table claimed with `FOR UPDATE SKIP LOCKED`; no Redis or
Celery. SQLite is supported for unit tests/local dev by keeping SQL portable (the queue
falls back to a single-worker lock on SQLite). **Consequences:** durable, inspectable jobs;
one fewer service. Revisit if queue latency matters.

## ADR-005 — Diagnosis v1 = executed fingerprints + strict consistency + abstention (2026-10-15)
**Context:** no labelled real-world data; claims must be explainable and falsifiable.
**Decision:** error models are executable mutants; predictions come from running them;
decisions follow methodology §4; output is counts, not probabilities.
**Consequences:** high precision, limited coverage (double bugs abstain); coverage is reported.
Better methods plug in via `DiagnosticMethod` and are compared by replay.

## ADR-006 — React + TypeScript SPA after the backend loop works (2026-10-15)
**Decision:** frontend begins at M4, typed from OpenAPI. **Consequences:** M1–M3 are
exercised through CLI and API tests; avoids building UI on unstable contracts.

## ADR-007 — Server-side sessions, Argon2id, three roles (2026-10-15)
**Decision:** no external IdP for the MVP. Dev-only stub auth in M3 is hard-disabled
outside `CODEADAPT_ENV=dev`. Full auth lands in M8, before any non-local deployment.

## ADR-008 — Data classes on every record (2026-10-15)
**Decision:** `data_class ∈ {real, synthetic, dev}` on users, submissions and derived
records; synthetic fixtures are generated by a separate path and never through student
accounts; research queries must filter explicitly. **Consequences:** synthetic results can't
silently mix into real-learner statistics.

## ADR-009 — Public repo holds only demo content; real content in a private repo (2026-10-15)
**Context:** the GitHub repository is public. Hidden tests, reference solutions and error
models must not be visible to study participants. **Decision:** this repo ships
`content/demo/` (explicitly *not secret*) for development and CI; real study content
lives in a separate private repository mounted through `CODEADAPT_CONTENT_DIR`.
**Status:** confirmed by the owner on 2026-10-15 (chose public repo + private content repo
over making this repository private).

## ADR-010 — uv, ruff, mypy strict, pytest (2026-10-15)
**Decision:** uv lockfile for reproducible installs; ruff for lint+format; mypy `--strict`
on `src/`; pytest with a `sandbox` marker for Docker-dependent tests (skipped with a reason
when Docker is absent; CI always runs them).

## ADR-011 — Sandbox containers run with an init process (2026-10-15)
**Context:** M1 testing showed that a submission running as PID 1 ignores default-action
signals, so the CPU rlimit (SIGXCPU) could not stop it. **Decision:** every sandbox
container uses `--init` (Docker's bundled tini). **Consequences:** the program is an
ordinary process; one extra PID counts against `--pids-limit`; signal exit statuses are
reported as 128 + N by the init and classified accordingly.

## ADR-012 — Content as TOML + C++ files; outcome signatures as the comparison unit (2026-10-15)
**Context:** problems need tests, probes, skills and executable error models in a format
authors can review in a diff. **Decision:** `problem.toml` (stdlib `tomllib`, no extra
dependency) plus plain C++ files; versions are content hashes. Behaviour is compared through
*outcome signatures* (normalised stdout, or runtime-error signal/exit, or limit kind), so
fingerprints, validation and diagnosis all use one definition of "behaves the same".
Authors also write `expected` outputs, and the executed reference must match them, which
catches harness and reference bugs. **Consequences:** a harness that prints
non-deterministic text (addresses, timing) would be rejected by validation, which is intended.

## ADR-013 — M3 slice conventions (2026-10-15)
* **Dev-only auth stub:** in `dev`/`test`, the `X-Dev-Role` header selects a fixed dev account
  (`data_class = dev`). It is disabled in production, where endpoints return 503 until M8.
  This keeps the slice testable without building auth twice.
* **Fingerprint cache:** the worker measures fingerprints the first time a
  `(problem version, environment)` pair is seen. It stores them with their validation
  report in `fingerprint_sets`, and refuses to diagnose against content that failed
  validation.
* **Queue claim:** an optimistic conditional `UPDATE` (expected state + attempt count). It is
  portable across SQLite and PostgreSQL, so `SKIP LOCKED` is not required (refines ADR-004).
* **Student projection:** hidden tests are shown only by number and `student_description`.
  An error model's `student_hint` is shown only for `HYPOTHESIS_SUPPORTED`. Model keys and
  descriptions never reach students. An end-to-end test asserts this.

## ADR-014 — CodeMirror 6 instead of Monaco (2026-10-15; supersedes the editor choice in ADR-006)
**Context:** Monaco is about 2–3 MB, loads web workers, and its React wrapper fetches from a
CDN by default. That is a third-party runtime dependency and a CSP problem for a study
deployment. **Decision:** CodeMirror 6 with `@codemirror/lang-cpp`, bundled locally and
lazy-loaded with the practice page (about 210 kB gzipped). **Consequences:** it has no
IntelliSense, which a learning platform does not want anyway.

## ADR-015 — Development compose stack uses SQLite and the host Docker socket (2026-10-15)
**Decision:** `compose.yaml` runs migrate, API, worker and the Vite dev server. The worker
mounts the host Docker socket so it can start sandbox containers. It is marked dev-only,
because the socket is root-equivalent; the production layout is decided in M8. It uses
SQLite on a shared volume because that is the tested configuration (PostgreSQL arrives with
M8 and its own tests).

## ADR-016 — Reliability channels: one repeat of failing tests, sanitiser build over all tests (2026-10-15)
**Context:** undefined behaviour can make output wrong, or right by accident, and a timeout
alone hides nothing about it. **Decision:** run the ASan + UBSan profile on every test, and
repeat only *failing* tests, once, to detect non-determinism. Passing tests are not
repeated: a non-deterministic pass is still a pass on that run, and the sanitiser covers
the main cause. Sanitiser findings exclude a test; the diagnosis treats exclusions under
rule 3. **Costs:** about twice the execution per submission, and the first fingerprint
measurement for a content version takes about 90 s locally. **Limits:** uninitialised
reads are not detected (no MSan in GCC).

## ADR-017 — Adaptation v1: append-only recommendations, criterion verdicts (2026-10-15)
**Context:** M6 needs a next-exercise policy and a way to judge the follow-up without
claiming learning. **Decision:** the policy (`rule_policy` v1) and the evaluation
(`criterion_check` v1) are pure functions over stored evidence. Their output goes into
append-only `recommendations` and `followup_evaluations` tables; a learner's open
recommendation is the latest one without an evaluation, so nothing is updated in place.
Each recommendation records its success criterion *before* the follow-up exists. Verdicts
are `criterion_met` / `criterion_not_met` / `not_comparable` rather than "improved",
because without a comparison condition a met criterion is equally consistent with an
easier problem. Candidate problems are limited to the index problem's family, and skills
are matched by key across problems. Adaptation runs after the diagnosis is committed, so a
failure in it is logged and never loses evidence. **Costs:** the ledger is rebuilt from
the learner's whole history on every diagnosis (fine at pilot scale; index it later if
needed). **Limits:** a recommendation can only target skills that the content's probes
and error models name, and its ranking ties are broken by slug, which is arbitrary but
deterministic.

## ADR-018 — Evaluation harness shares the worker's evidence path; dev role switch in the UI (2026-10-15)
**Context:** M7 must report methodology §6.1 metrics, and a harness that collected
evidence differently from the worker would measure a different system. **Decision:**
evidence collection moved to `evidence/collect.py`, used by both the worker and
`codeadapt-eval`. The harness writes no database rows and its reports carry no
timestamps, so reruns compare byte for byte. Held-out cases live in `eval/heldout/` with a
`cases.toml` manifest per problem (`truth` = error-model key, `correct` or `unmodelled`).
The research API reports counts only, since stored submissions have no ground truth.
Until real authentication exists (M8), the web app has a "development role" selector that
sets the `X-Dev-Role` header; the API ignores it outside development. **Limits:** the
harness runs every case's evidence concurrently, so runtime grows with the sandbox host's
capacity; cross-environment reproducibility is not yet measured.

## ADR-019 — Evidence no stronger than its support: explained-failure ledger, behaviour groups, qualified hypotheses (2026-10-15)
**Context:** the lower-bound design review found that (a) the ledger charged every failing
test to every skill its probes name, whether or not anything explained the failure, and
(b) `min_support` counts tests, so a model whose supporting tests all show one behaviour
(E2 `hi_init_last_index`, in all three demo problems) looked better supported than it is.
The owner asked for these to be fixed, and for the stricter support rule (C6) to be
compared with v1 on held-out cases before any adoption. **Decision:**
* *Ledger (C5).* A failed test enters the skill ledger only when a supported diagnosis
  explains it, and then only under the selected model's skill (`explained_by` records the
  model). Failures in ambiguous, unmodelled, insufficient or unreliable attempts stay in
  the stored submission but are not skill evidence. Passed and excluded tests are
  attributed through probes as before. Policy version → `rule_policy` 1.1.
* *Behaviour groups.* `diagnosis/groups.py` measures them; validation and diagnosis share
  it. Diagnosis v1.1 records `support_behaviours` and, for a supported diagnosis resting on
  one group, `evidence_strength = single_behaviour` with a qualification. Its *decisions*
  are those of v1. A supported diagnosis that is single-behaviour, or whose model has a
  `known_limitation`, is a *qualified hypothesis*: the student sees "one possible cause to
  check", the recommendation says the pattern "has more than one possible cause", and its
  rationale carries `qualified_hypothesis`. The follow-up still targets the skill.
* *C6 candidate.* `v2-candidate` (same method, `min_behaviours = 2`) turns single-group
  diagnoses into `INSUFFICIENT_EVIDENCE`. It is selectable in `codeadapt-eval --method`
  only; the worker keeps v1.1. Adoption is an owner decision (see the review-resolution
  report for the measured trade-off).
* *Follow-up relation.* Each evaluation records whether the follow-up was the same
  problem, equivalent practice or a linked transfer problem (`criterion_check` 1.1,
  migration 0003). A met criterion is reported as passing the follow-up's tests, never as
  mastery or demonstrated transfer.
* *Declared intent (C4).* `problem.toml` gains per-test `purpose` and `distinguishes`,
  per-model `known_limitation` and `[curriculum]` links; validation errors on a declared
  `distinguishes` that the measurement contradicts. Calibration cases (written after a
  design analysis) live in `eval/calibration/` and are never pooled with held-out ones.
**Costs:** behaviour groups are relative to the modelled programs, so adding a model can
change a diagnosis's strength; content changes are therefore versioned as before.
**Limits:** a qualified hypothesis is still a hypothesis from the modelled error space;
the qualification describes the evidence, not the probability of being right. The O(log n)
requirement is not assessed by any test (see methodology §4).

## ADR-020 — Sandbox runs under load: longer kill wait, untrusted streams are infrastructure errors (2026-10-15)
**Context:** on busy hosts (locally and on CI), `docker kill` of a timed-out container
sometimes exceeded its 15 s limit, aborting a job, and once a run reported exit 0 with
empty stdout, which made validated content look non-deterministic. 200 stressed local
runs did not reproduce the lost output. **Decision:** the kill wait uses the general
60 s CLI limit (the workload stays bounded by its CPU rlimit, memory and pids limits, and
`rm -f` still runs afterwards). When the `docker run` client's exit status differs from
the container's own exit code on a run that ended by itself, the run is classified as an
infrastructure error, never as program output. Fingerprint measurement re-measures an
infrastructure error up to 3 times; program behaviour is never re-measured, so real
non-determinism is still reported. **Limits:** if a lost-output run reports matching exit
statuses, this check does not catch it. A harness end-of-output marker would, but it
changes every problem's output contract, so it is proposed rather than done.

## ADR-021 — Modelling architecture: deterministic diagnosis plus a later Bayesian learner model (2026-10-16)
**Context:** the owner set the long-term direction (project chat, 2026-10-16): keep the
execution-grounded diagnosis, and add Bayesian learner modelling later as a separate layer.
**Decision:** four components with separate responsibilities, each testable on its own:
1. *Diagnostic engine* (fingerprint consistency, ADR-005/019). It identifies which known
   implementation-error patterns are consistent with one submission's execution evidence,
   or abstains. It stays deterministic. It is not to be replaced by an ML or LLM bug
   classifier: there is no labelled real-student dataset, and the current method is
   reproducible, interpretable and traceable.
2. *Skill-evidence layer* (today: the ledger, `adaptation/ledger.py`). It maps reliable,
   diagnosis-supported observations to skills, keeps their uncertainty, and makes no
   unsupported attribution. Since ADR-019, failures from ambiguous, unmodelled,
   insufficient or unreliable attempts are not skill evidence; infrastructure failures
   never reach it.
3. *Bayesian learner model* (planned, **not implemented**). It updates estimated skill
   mastery as valid evidence accumulates across attempts and problems.
4. *Recommendation policy* (today: `rule_policy`). It chooses next activities from the
   learner model, prerequisites, curriculum links and available exercises.

A diagnosed implementation pattern is never treated as proof of a misconception or of a
lack of mastery. **Sequencing:** the interface between the four components (the evidence
each receives, how uncertainty is represented, which observations are excluded) is
documented first, for the owner's review. Only when the evidence layer is reliable enough is a
separate, testable BKT milestone proposed. Its initial probabilities and its transition,
guess and slip parameters are documented as assumptions until validated. Synthetic
experiments may test implementation behaviour, but are never presented as calibration on
real students or as learning gains. **Supersedes** the methodology §5 note that placed
BKT only after a cohort study: BKT is part of the intended architecture, gated on the
evidence layer and the reviewed interface, and its parameters stay assumptions until real
data validates them.
