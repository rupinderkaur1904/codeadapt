# Limitations and future work (as of 2026-10-24)

Each item says what is limited, the evidence for it, and what would address it. Numbers come
from [evaluation/summary.md](evaluation/summary.md).

## Evidence about the diagnostic method

| # | Limitation | Evidence | What would address it |
| --- | --- | --- | --- |
| L1 | No independent test data. Held-out programs were written by the error-model author; mutants were generated and labelled by the same AI system that works on the project. | critical review 2026-10-21; VAL1-A/A2 reports | Programs by other people: VAL1-B (pre-registered, deferred) or real rejected submissions (PC1, blocked) |
| L2 | Near-circularity. Every correctly diagnosed held-out case produced exactly its bug model's output on 500 random inputs (it was effectively that model), and the unmodelled cases were far from every model. | critical review §3 | Cases chosen by someone else; mutation audits (done) |
| L3 | Low coverage. Under v1.3, about 9% of incorrect mutants (30/323) and 14/26 held-out cases get a named error. | adr030-2026-10-23 | Better failing-case feedback (proposal); more discriminating tests per problem |
| L4 | "0 wrong" rests on small denominators (30 named mutants, 14 held-out). | same | Larger, independent samples |
| L5 | One algorithm family (binary search, 4 problems) with shared bug models, so evidence across problems is not independent. | content/demo | New families designed for diagnosis (CE1.2/1.3 paused) |
| L6 | Strict consistency: two bugs, or one bug plus noise, give `unmodelled_behaviour`. | methodology §4 | A noise-aware or compositional method, compared on stored evidence |
| L7 | Complexity is not assessed: a linear scan passes. | methodology §4 | An instrumented harness counting comparisons |
| L8 | count-occurrences can no longer name its only equality model (ADR-030 cost). | adr030-2026-10-23 | A test on which that model prints something other than 0 |

## Learner model and recommendations

| # | Limitation | Evidence | What would address it |
| --- | --- | --- | --- |
| L9 | BKT parameters are assumptions (`bkt-params-assumed-1`); estimates swing widely across plausible values (e.g. 0.52–0.99 after two corrects). | bkt-sensitivity-2026-10-17 | Fitting on real data; until then researcher-only |
| L10 | Skill maps (problem → skill) are unvalidated modelling choices. | ADR-021/023 | Expert review; real-data checks |
| L11 | The recommendation policy is a transparent rule set over a small bank, effectively a fixed sibling lookup; it ignores prerequisites and uncertainty. | critical review; policy 1.4 | More content; a policy evaluated on learner outcomes |
| L12 | No learning effect has been measured; no claim of improved learning is possible. | — | A study with real learners and a suitable design |
| L19 | Rule C gives a `correct` observation to any skill whose every probing test passed, whatever else the program did. A program that prints 0 on every count-occurrences test (abstained on, rule 8a) still earns `problem_specification` = correct from the absent-target tests. Evidence is per test property, not per program understanding. | pinned in `tests/sandbox/test_adaptation_end_to_end.py` (2026-10-24) | An owner decision on whether abstained or largely failing attempts should give positive evidence (an evidence-policy change, not made). Measured on 421 synthetic mutants under v1.3: incorrect programs gave 94 `correct` and 28 `incorrect` observations; options and a recommendation in docs/reviews/2026-10-25/l19-policy-options.md |
| L20 | Some skill attributions are not unique even when the diagnosis is unqualified. min-capacity `strict_day_limit` and `full_day_overflows` (mapped to `equality_handling`) are output-identical on every valid input to programs with a counting or specification error, so a named diagnosis may put an `incorrect` observation on the wrong skill. rotated-min `compares_with_lo` is attributed to its effect (`search_space_boundaries`), not its cause, which no skill describes. **Owner principle (2026-10-25):** where two distinct error causes are observationally indistinguishable on the valid input domain, the system must not claim to distinguish them. **Resolved for min-capacity by ADR-032 (owner option b, 2026-10-25):** both models carry a documented `known_limitation`, so diagnoses are kept but qualified and add no `equality_handling` evidence or BKT update. Attempts stored against the earlier min-capacity content version keep that version's snapshot (ADR-023 D4); none exist outside dev/test databases. rotated-min is not provably non-unique and is unchanged. **Bank expansion (2026-10-25):** each of the 13 new problems was checked against hand-written alternative-cause programs on 400 random inputs (not exhaustive). Three cross-skill equivalences were found and take the same route (`stock-profit/ignores_order`, `container-water/moves_taller`, `dedup-sorted/returns_last_index`); same-skill equivalences are listed in each design record. **Search of six provisional binary-search problems (2026-10-25, owner action 3):** 13 of the 29 models that v1.3 can name unqualified in upper-bound, exact-search, last-occurrence, rotated-search, peak-index and integer-sqrt are output-identical, on every committed test and on exhaustive small and seeded random domains, to a program whose cause belongs to a different skill (11 clear-cut, 2 contestable); 12 of the 13 are correct solutions to a misread task. **S1 applied 2026-10-26 (owner-approved, ADR-036):** the 11 clear-cut models now carry a `known_limitation`, so their diagnoses are qualified and add no `incorrect` evidence. The 2 contestable models (#3 upper-bound `returns_last_not_greater`, #13 integer-sqrt `returns_lo_closed`) are unchanged and still give `incorrect` evidence; the written analysis recommends keeping them. **Four original problems searched 2026-10-26 (investigation only):** of 15 nameable models, 4 have a clear-cut cross-skill twin (lower-bound `upper_bound_confusion`, last-less-than `uses_le` and `clamps_to_zero`, first-true `none_sentinel`), 4 a contestable one and 2 an equivalent program with no plausible cause. **S1 applied to O1–O4 2026-10-26 (owner request, ADR-037):** the four clear-cut models now carry a `known_limitation`, so their diagnoses are qualified and add no `incorrect` evidence; `equality_handling` in last-less-than becomes positive-only, and the lower-bound demo program `upper_bound_closed.cpp` now gets qualified feedback. The contestable (O5–O8) and unsupported (O9–O10) models are unchanged and still give `incorrect` evidence (docs/reviews/2026-10-26/l20-original-s1.md). | docs/reviews/2026-10-25/skill-mapping-review.md; docs/content-design/expansion-2026-10-25/; docs/reviews/2026-10-25/l20-search.md; docs/reviews/2026-10-26/l20-contestable-cases.md; docs/reviews/2026-10-26/l20-search-original.md | ADR-032, ADR-036 and ADR-037 done; open for owner decision: the contestable cases (#3, #13, O5–O8), S2 and the S3 admission check |
| L21 | After a pass, when every *recommendable* problem of the family has a pass (or the family has none, as in every non-binary-search family since the 2026-10-25 expansion), the action is `none`. The rationale note says "every problem in the family has an attempt with no failure observed" and the student message says "Every problem in this family has an attempt of yours with no failing tests"; both ignore non-recommendable problems and are false whenever one is unpassed. **Audit 2026-10-25:** this also happens in binary search once lower-bound, count-occurrences and last-less-than are passed (since policy 1.3). Code: `policy_v1.py` 166–180, `api/recommendation.py` 35–39. **Wording corrected 2026-10-25 (owner-approved, no decision change):** the note now says "every recommendable problem", and the student message says "There is no further problem to recommend here yet. You can choose any problem from the list." Recommendations stored before the change keep the old note. What remains open is the behaviour: no next step after a pass in these families. Supported and ambiguous diagnoses fall back to a retry of the same problem. | ADR-033; policy 1.4; docs/reviews/2026-10-25/expansion-audit.md §3 | A policy revision (options in the audit), or recommendable problems in those families once the research criteria allow it |
| L22 | The five skill keys of the new families (ADR-033: `index_range`, `accumulator_init`, `tie_resolution`, `update_rule`, `output_contract`) are broad and defined by the author. Evidence pools across problems and families by key, so an `index_range` mistake in a sliding-window problem and one in an array problem count as the same skill; whether students' errors actually transfer that way is untested. **Migrated 2026-10-26 (ADR-034):** `index_range` and `update_rule` are retired and replaced by `loop_bounds`, `range_inclusion`, `window_maintenance`, `pointer_movement` and `running_state`; old observations keep their old keys and are shown as deprecated. The new keys are narrower but equally author-defined and untested for transfer. Each new problem has 7–8 held-out cases written by the models' author; one (second-largest `after_max_only.cpp`) exposed a wrong design claim and was fixed after it was seen, so it is no longer an independent check. | ADR-033; docs/evaluation/expansion-2026-10-25/ | Independent programs for these families; a skill-map validation before any of them becomes recommendable; revised taxonomy applied (ADR-034), optional splits not made |
| L23 | Complexity bounds and the technique a problem assesses are not verified. All 25 statements state a complexity bound and 14 ban named library calls, but a linear scan or a banned call passes every test, and rule C then gives `correct` observations (audit D1). A `correct` observation means no failure on the probing tests, not use of the intended technique. **Partly addressed 2026-10-26 (ADR-035):** an attempt whose source names a banned call gives no skill observations. The check is a static token match: it does not show which algorithm was used or its complexity, and a hand-written linear scan or a macro still passes and earns `correct`. Attempts on content versions registered before the change keep their evidence. **Audit 2026-10-26:** (a) a student's own lambda or function object named like a banned call (`auto pow = [](long long v) {...}`) was wrongly found; fixed, with tests. (b) The detector is not versioned: its result is recomputed from the stored source whenever evidence is read, so a change to it (such as fix a) applies to earlier attempts on banned-name versions. Only dev and test data exist; recording a detector version with each attempt would close this. (c) A program that defines its own function or variable of a banned name and also calls the library function unqualified is missed. | docs/reviews/2026-10-25/expansion-audit.md §5.2; docs/proposals/d1-technique-evidence.md; ADR-035 | Multi-query tests only if complexity becomes an assessed outcome; owner review of the counting choice (a banned-name attempt consumes the counted opportunity) |

## Future work, in order of value for the research question

1. Independent programs (PC1 if unblocked, otherwise VAL1-B), evaluated with the pre-registered
   protocols.
2. Failing-case feedback as the main experience (proposal), since that is what most students see.
3. Evidence that the new families' skill keys (ADR-033, added 2026-10-25 with 13 non-recommendable
   problems) describe errors that recur across problems.
4. Only after real data: fitting BKT parameters, and validating skill maps.
