# CodeAdapt: engineering release report (2026-10-26)

**Status.** A demonstrable research prototype on branch `claude/project-thread-dyivyy`. It is
not deployed. It has not been used by or evaluated on real students.

**This report separates five things:**

1. what is implemented and tested;
2. known limitations;
3. provisional or unreviewed content;
4. synthetic results;
5. open research questions.

**Engineering completion is not research validation.** No part of CodeAdapt has real-student
diagnostic accuracy, calibrated BKT parameters, or evidence of improved learning, and none is
claimed.

## 1. Architecture and data flow

```
Student code ─► API (FastAPI) ─► job queue (DB) ─► worker ─► Docker sandbox (runc; gVisor tier tested in CI)
                                                       │
                     compile, run every test (CPU/wall/memory/output limits, end-of-output marker)
                                                       │
                     observations (reliable / excluded, repeat runs, sanitizer build)
                                                       │
                     diagnosis: fingerprint_consistency 1.3 (v1.1, v1.2 selectable)
                                                       │
     ┌─────────────── evidence ledger: skill observations (rule C, explained failures, D1, S1)
     │                                                 │
     ▼                                                 ▼
 LM1 BKT (researcher-only,                  recommendation policy 1.4 (rules over the ledger)
 assumed parameters)                                   │
     │                                     follow-up evaluation on the next attempt
     ▼                                                 │
 researcher views: trace, learner model,      student views: feedback, next step, my attempts
 metrics, submissions
```

The components, data model and API are in docs/architecture.md. The decision log, ADR-001 to
ADR-037, is in docs/decisions.md.

**Content.**

- Every problem is a versioned directory: statement, harness, reference, tests, error
  models and a skill map. Its content version is a hash over its files.
- Each attempt is attributed with the skill-map snapshot of its own version (ADR-023 D4).
  Earlier versions stay registered, so historical evidence is never rewritten.

## 3. Diagnosis and evidence eligibility

**Diagnosis.** `fingerprint_consistency` 1.3 (methodology.md §4; ADR-005, ADR-027, ADR-030)
compares the reliable outcomes with the reference and with each error model's measured
fingerprint. Its outcomes are:

- **`hypothesis_supported`**, a named model. It is qualified when the model's support spans
  a single behaviour group.
- **`ambiguous`**.
- **`unmodelled_behaviour`**.
- **`insufficient_evidence`** (rules 7, 8a, 8b).
- **`non_termination_observed`** (rule 4b: a time limit is a symptom and never named).
- **`no_failure_observed`**.
- **Compile and infrastructure outcomes.** These are never evidence.

**Skill evidence** (ADR-023, ADR-032 to ADR-037). The rules are:

- **Passed tests:** rule C gives a `correct` observation to a skill whose every probing test
  passed (L19, unchanged).
- **Failed tests:** they count only through an **unqualified** supported diagnosis, as
  `incorrect` on the model's skill. Abstentions, ambiguity and qualified diagnoses add no
  `incorrect` observation.
- **Qualified diagnoses.** A model with a `known_limitation` is qualified: a single
  behaviour group, or an attribution that is not unique (L20 S1: ADR-032, ADR-036, ADR-037).
  The diagnosis, trace and recommendation are kept, the feedback is qualified, and there is no
  `incorrect` observation and no BKT update.
- **D1 (ADR-035).** In the 14 problems that ban named library calls, an attempt whose source
  names one gives **no** skill observations. It still runs, is diagnosed, gets feedback and a
  recommendation, and counts as an attempt; it consumes the LM1 counted opportunity. The check
  is a static token match after removing comments and literals. It shows nothing about the
  algorithm or its complexity (L23).
- **Positive-only skills.** Where no model can give a skill `incorrect` evidence, the
  problem's `positive_only_skills` reason says so. 12 skills are declared. The researcher
  learner-model view now shows them per skill. 8 more are positive-only only through
  diagnosis rules 4b and 8a; they are listed in the bank status matrix §3, not yet declared.

## 4. Taxonomy and BKT configuration

**Taxonomy.** `backend/src/codeadapt/content/taxonomy.py` (ADR-034).

- **Binary search:** `search_space_boundaries`, `loop_termination`, `equality_handling`,
  `problem_specification`.
- **New families:** `loop_bounds`, `range_inclusion`, `window_maintenance`,
  `pointer_movement`, `running_state`, `accumulator_init`, `tie_resolution`,
  `output_contract`.
- **Retired:** `index_range` and `update_rule`. They keep their historical definitions and
  are shown to researchers as deprecated.

The skill maps are author-defined and unvalidated (L10, L22).

**LM1 BKT** (ADR-025).

- **Parameters:** `bkt-params-assumed-1`, with p_init 0.3, p_learn 0.1, p_guess 0.2 and
  p_slip 0.1. These are **assumptions, not fitted**.
- **Counting:** only the first reliably evaluated attempt per problem version is counted.
- **Display threshold:** 3 counted observations from 2 problems.
- **Labelling:** every value reads "estimated under assumed parameters".
- **Use:** researcher-only. It is not shown to learners and not used by any policy.

## 5. Recommendation policy

Policy 1.4 (`adaptation/policy_v1.py`; methodology.md §5) is a transparent rule set over the
ledger. Its rules are `hypothesis_supported`, `ambiguous`, `no_failure_observed`, `abstained`
and `not_evaluated`. Its actions are a new problem, a retry, or none (L21).

- Only recommendable problems are chosen.
- A qualified hypothesis keeps its rule and target and is marked in the rationale.
- Nothing in this stage changed the policy. On 442 synthetic one-attempt histories,
  rule, action, problem, target skills, review flag and criterion are identical to
  `f752a51`. The only difference is `qualified_hypothesis` for the four ADR-037 models.

## 9. Setup and demo

**Setup** (docs/development.md):

```bash
docker build -t codeadapt-sandbox:gcc14.2-1 sandbox/
cd backend && uv sync && uv run pytest tests/unit -q
CODEADAPT_REQUIRE_SANDBOX=1 uv run pytest tests/sandbox -q     # ~40 min locally
cd ../web && npm ci && npm run lint && npm run typecheck && npm test && npm run build
npm run e2e                                                      # Playwright, needs Docker
```

**Demo** (docs/demo.md):

```bash
cd backend
export CODEADAPT_ENV=dev CODEADAPT_DATABASE_URL=sqlite:////tmp/codeadapt-demo.sqlite3
uv run alembic upgrade head
uv run uvicorn codeadapt.api.app:create_app --factory --port 8000 &
uv run codeadapt-worker &
cd .. && python3 docs/demo/run_demo.py
```

Then:

1. Open the web UI with `cd web && npm run dev`, or run `docker compose up --build`.
2. Choose Lower bound on `/problems`.
3. Submit, then switch to the researcher role and open the trace and the learner model.

Describe the eight provisional problems as unreviewed. Since ADR-037, the lower-bound
`upper_bound_closed.cpp` example gets qualified feedback. Use a `stops_at_first_match`
program to show an unqualified named diagnosis.

## 10. Known limitations

The full list is in docs/limitations.md. The main ones:

- **L19:** rule C credits any skill whose every probing test passed, including on largely
  failing or abstained attempts.
- **L20:** attributions are non-unique where outputs are indistinguishable. The four
  contestable cases (#3, #13, O5–O8) still give `incorrect` evidence.
- **L21:** no next step after a pass in the new families.
- **L22 and L10:** skill keys and maps are author-defined and unvalidated.
- **L23:** complexity and technique are unverified. D1 is a static token match, and its
  detector is not versioned.
- **L9:** BKT parameters are assumed, and the estimates are very sensitive to them.
- **L11 and L12:** the recommendation policy is a small rule set, and no learning effect has
  been measured.
- **L13 to L16 (platform):** not deployed, gVisor is tested only in CI, the lost-output root
  cause is unknown, and the sandbox tests are slow.

## 13. Open research questions and the next milestone

**Open questions:**

- **The end-of-search question:** is "which variable to return or record at the end" a
  `problem_specification` error? It covers five models.
- **Undeclared-skill twins:** may a twin whose cause belongs to an undeclared skill count as
  cross-skill?
- **L19:** whether rule C should credit largely failing attempts.
- **D1 counting:** whether a banned-name attempt should consume the counted opportunity.
- **The provisional problems:** the review of the eight, and any recommendable status for the
  new families.
- **Validation:** of skill maps and transfer, and of BKT parameters, which needs real data.

**Next research milestone.** Validation on programs not written by the model author, so that
diagnostic accuracy and attribution can be measured independently. The candidates are:

- the deferred VAL1-B study, which needs recruitment approval;
- the CodeNet Phase E route. Its gate stays closed: no code-level permission basis is
  recorded, and nothing restricted was accessed in this stage.

Until then, every result above stays synthetic.
